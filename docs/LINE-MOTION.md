# Построчный выход текста поверх плёнки

**Версия стека, под которую написано:** `gsap@3.15.0`, `@gsap/react@2.1.2`, React 19, Vite.
Всё, что ниже про API, сверено с документацией GSAP 3.13+ и с исходником
`node_modules/gsap/SplitText.js` 3.15.0 — не по памяти о старых версиях.
Числа — из `DESIGN-SYSTEM.md` §5, §6, §8; ссылки на источники в конце.

**Файлы в `src/` этот документ не правит.** Раздел 11 — список изменений для того, кто правит.

## 0. Просьба, переведённая в техническое требование

> «Хочу, чтобы с помощью GSAP стелилась строчка за строчкой. Двигается кадр — и строчка
> за строчкой стелется».

Разложим на три требования, каждое проверяемо:

| Что сказано | Что это значит в коде | Как проверить |
|---|---|---|
| «двигается кадр — и строчка стелется» | **чем строка вызвана** — прокруткой, а не таймером, который прокрутка только запустила. Остановил палец в середине абзаца — раскладка встала | остановиться на середине блока: часть строк уложена, часть ещё нет |
| «строчка за строчкой» | **порядок и зазор** видимы. Строки не выезжают пачкой | снять видео 60 fps, посчитать кадры между стартами соседних строк |
| «стелется» | не «выехала снизу», а **разворачивается от края, откуда читают**, с инерцией в хвосте | закрыть половину экрана: движение должно идти вдоль строки, а не поперёк |

Третье требование — самое содержательное и его сейчас нет вообще. Текущий `Lines.tsx`
двигает строку **поперёк** её собственного направления (`yPercent: 108` — снизу вверх).
Это «текст выехал». «Стелется» — это движение **вдоль** строки, от начала чтения к концу.

## 1. Что сейчас в `Lines.tsx` и что в нём сломано

Разбор текущего файла. Пять пунктов, три из них — настоящие дефекты, а не вкусовщина.

### 1.1. 🔴 Скорость камеры считается не в тот момент

```tsx
onSplit(self) {
  const { duration, stagger: autoStagger } = timing()   // ← вызывается ПРИ РАЗБИЕНИИ
  return gsap.from(self.lines, { duration, stagger: ..., scrollTrigger: {...} })
}
```

Комментарий в файле утверждает: «Тайминг берётся в момент выхода строк, а не при
монтировании». Фактически `onSplit` выполняется **один раз при создании SplitText**, то
есть при монтировании компонента, когда `progressRef.current` ≈ 0 для всех одиннадцати
блоков сразу. `duration` запекается в твин и больше не меняется.

Итог: вся работа `render/export_motion.py` + `motion.ts` сейчас **не доезжает до экрана**.
Все блоки выходят с длительностью, посчитанной для скорости камеры в точке 0.

### 1.2. 🔴 `mask: 'lines'` + `line-height < 1` = срезанные буквы

`SplitText` реализует маску так (исходник 3.15.0, строки 273–280):

```js
let maskEl = el.cloneNode();
el.replaceWith(maskEl);
maskEl.appendChild(el);
maskEl.style.overflow = "clip";
```

Маска — клон строкового `div`, то есть её высота **равна line-box строки**. Обрезка идёт
по padding-box. А в `index.css`:

```css
.t-display { line-height: calc(0.86 + var(--lang-leading)); }   /* 0.86 / 0.92 в HE */
.t-h2      { line-height: calc(1.04 + var(--lang-leading)); }
```

Content area у наших гарнитур ≈ 1.15–1.25 em. При `line-height: 0.86` буквы вылезают за
line-box примерно на **0.17 em сверху и снизу** — и маска их режет. На `שחור` кеглем
9.5 rem это ~26 px срезанной верхушки. Постоянно, не только во время анимации.

**Проверить за 10 секунд** (консоль на проде, любой язык):

```js
document.querySelectorAll('[class*="-mask"], .line-mask').forEach(m => {
  const l = m.firstElementChild
  if (l && l.scrollHeight > m.clientHeight + 1)
    console.warn('режет', m.clientHeight, '<', l.scrollHeight, l.textContent.slice(0,20))
})
```

Лечение — в 4.4 (padding на маске + пересчитанный `yPercent`).

### 1.3. 🔴 `useGSAP` с `dependencies` не откатывает контекст при смене локали

Исходник `@gsap/react@2.1.2` (`src/index.js:35`):

```js
deferCleanup = dependencies && dependencies.length && !revertOnUpdate;
```

При `deferCleanup === true` откат контекста **отложен до размонтирования**. У нас
`dependencies: [locale, delay, stagger]` и `revertOnUpdate` не задан → на каждой смене
языка колбэк выполняется заново, а старые твины и ScrollTrigger'ы **не убиваются**.

Сам `SplitText` частично спасает (конструктор реверсит предыдущий сплит того же
элемента — строка 177 исходника), но ScrollTrigger'ы накапливаются: три переключения
языка = **44 живых триггера** вместо 11, и все дёргаются на каждом кадре прокрутки.
Плюс `return () => { clearTimeout(...); split.revert() }` из колбэка при `deferCleanup`
тоже не вызывается на смене зависимостей.

**Фикс:** `revertOnUpdate: true`.

### 1.4. `toggleActions: 'play none none reverse'` — не то, что просят

`reverse` на `onLeaveBack` означает: уехал вверх — текст уползает обратно под маску.
Само по себе допустимо, но это ровно тот класс поведения, который убивает читаемость на
скрабе (раздел 3), и он не связан с камерой никак.

### 1.5. Failsafe 2.5 с — почти пустышка (но не вредная)

```tsx
const failsafe = window.setTimeout(() => {
  if (!shown) gsap.set(split.lines, { yPercent: 0, opacity: 1 })
}, 2500)
```

Что с ним не так:

- **Срабатывает не на аварии, а на норме.** Блок 5 лежит в пяти экранах ниже; через 2.5 с
  `shown === false` совершенно законно, и failsafe «показывает» строки, которые и так
  видимы (`immediateRender: false` — они никогда не прятались). Потом пользователь
  доезжает, ScrollTrigger играет `gsap.from` — всё работает. То есть в 10 случаях из 10
  это no-op.
- **Не покрывает настоящую аварию** — когда `start/end` посчитаны до раскладки шрифтов и
  блок не триггерится никогда.
- **Знает список свойств.** Сейчас `{yPercent, opacity}`. Добавим сдвиг и skew на маске —
  failsafe про них не знает и оставит строку косой/сдвинутой.

Что в нём **правильно и надо сохранить**: `immediateRender: false`. Пока твин не начался,
строки — обычный видимый текст. Это сильнее любого таймера: если JS умер до старта,
пользователь видит текст, а не пустоту. Новая схема (раздел 4) это свойство сохраняет.

Замена — в разделе 10.

## 2. Каталог механик: шесть приёмов и чего каждый стоит

Все примеры — на одной строке; в бою — в цикле по `self.lines`. `e-out` — наш токен
`cubic-bezier(0.16, 1, 0.30, 1)`, зарегистрированный через `CustomEase` (см. 4.2).

### M1. Маскированный выезд (то, что сейчас)

```js
gsap.fromTo(line, { yPercent: 112 }, { yPercent: 0, duration: 0.9, ease: 'e-out' })
// SplitText: { type: 'lines', mask: 'lines' }
```

**Как выглядит.** Строка выезжает снизу из-под жёсткого края, как из щели.
**Когда уместна.** Универсальный базовый слой; на нём стоит половина Awwwards.
**Цена.** Composite-only: только `transform`. Один дополнительный DOM-узел на строку
(маска). Самый дешёвый приём в списке.
**Минус.** Ровно нулевая связь с направлением чтения. Читается как «текст выехал».

### M2. Штора по строке через `clip-path`

```js
gsap.fromTo(line,
  { clipPath: rtl ? 'inset(0 0 0 100%)' : 'inset(0 100% 0 0)' },
  { clipPath: 'inset(0 0 0 0)', duration: 0.75, ease: 'e-out' })
// mask не нужен вовсе
```

**Как выглядит.** Строка проявляется слева направо (в HE — справа налево), как будто её
пишут. Самый буквальный ответ на слово «стелется».
**Когда уместна.** Одиночная короткая фраза, слоган, цитата. На абзаце из 5 строк
превращается в печатную машинку — читать невозможно.
**Цена.** `clip-path` в composite-tier по классификации Motion, но GSAP переписывает
inline-стиль каждый кадр из main-thread → style recalc + инвалидация отрисовки строки
каждый кадр. Площадь строки мала, так что это дёшево, но не бесплатно; при живом
WebGL-канвасе под текстом — второй выбор, не первый.
**Плюс над M1.** Не нужна маска → **не режет выносные элементы**, проблема 1.2 исчезает.

### M3. Разворот по оси X с перспективой

```js
gsap.set(container, { perspective: 900 })
gsap.fromTo(line,
  { rotateX: -72, transformOrigin: '50% 0%', opacity: 0 },
  { rotateX: 0, opacity: 1, duration: 0.85, ease: 'e-out' })
```

**Как выглядит.** Строка откидывается сверху, как створка. Очень «дорого» на одиночном
крупном заголовке.
**Когда уместна.** Ровно один раз на странице, на дисплейном уровне. На корпусе — китч.
**Цена.** Transform-only, но 3D-контекст: элемент получает собственный слой композитора
навсегда, а текст в 3D-трансформе на Android рендерится **без субпиксельного сглаживания**
— тонкие серифы Frank Ruhl Libre замылятся и не расплывутся обратно, пока слой жив.
Обязателен `gsap.set(line, { clearProps: 'transform' })` по завершении.
**Вердикт.** Для `שחור` в первом блоке — можно. Для абзацев — нет.

### M4. Стелющаяся строка ← **рекомендуется**

Маска даёт вертикальное раскрытие, сдвиг по горизонтали — направление, `skewY` с
точкой отсчёта у края чтения — инерцию хвоста.

```js
const rtl  = getComputedStyle(line).direction === 'rtl'
const sign = rtl ? 1 : -1                      // старт со стороны, откуда читают
const origin = rtl ? 'right center' : 'left center'

gsap.timeline()
  .fromTo(mask, { x: sign * drift, skewY: skew, transformOrigin: origin },
                { x: 0, skewY: 0, duration, ease: 'e-out' }, 0)
  .fromTo(line, { yPercent: hidden },
                { yPercent: 0, duration, ease: 'e-out' }, 0)
```

**Как выглядит.** Строка не выезжает, а **раскатывается**: голова встаёт первой, хвост
догоняет с небольшим наклоном, который выпрямляется. Вектор движения — вдоль чтения.
**Почему сдвиг на маске, а не на строке.** Строка внутри маски обрезана; сдвинув её
на −24 px, мы срезаем первые буквы. Сдвиг всей маски целиком горизонтально ничего не
обрезает. Цена — маска на 20 px выходит за колонку, но у нас `px-6` (24 px) поля, так что
в экран помещается. Вариант «сдвигать строку внутри маски, буквы выползают из-под края»
тоже красив, но на дисплейном кегле голова слова заметно рубится.
**Цена.** Два `transform` вместо одного, оба composite-only. Плюс один твин на строку
вместо одного на блок — для абзаца из 5 строк это 5 таймлайнов вместо 1; на нашем
масштабе (≈40 строк на всю страницу) незаметно.
**Числа** — в 4.4.

### M5. Появление словами внутри строки

```js
SplitText.create(el, { type: 'lines,words', mask: 'lines', ... })
gsap.from(lineWords, {
  yPercent: 100, duration: 0.55, ease: 'e-out',
  stagger: { each: 0.026, from: rtl ? 'end' : 'start' },
})
```

**Как выглядит.** Слова внутри строки набегают волной. Ощущение «текст произносится».
**Когда уместна.** Одна ключевая фраза на весь сайт — например, манифест в первом блоке.
Жёсткий потолок: **≤ 12 слов**. Дальше глаз перестаёт собирать фразу.
**Цена.** 5–9× DOM-узлов. Анимируется по-прежнему только transform → композитор
справится, но `will-change` на 60 словах одновременно — это уже реальная память
композитора рядом с 144-кадровым атласом.
**🔴 Отдельный запрет для нас:** в HE-локали разбиение на слова ломает bidi там, где в
строке смешанный набор (цены, часы, латинские названия). Каждое слово становится
отдельным inline-block, и алгоритм двунаправленности перестаёт их переупорядочивать. См.
раздел 6.

### M6. Blur-to-sharp

```js
gsap.fromTo(line, { filter: 'blur(5px)', opacity: 0 },
                  { filter: 'blur(0px)', opacity: 1, duration: 0.8, ease: 'e-out' })
```

**Как выглядит.** Наводка на резкость. Рифмуется с камерой буквально — поэтому соблазн
велик.
**Честная цена — самая высокая в списке.** `filter` формально composite-tier, но каждое
изменение радиуса требует **новой растеризации содержимого слоя**. Текст — худший
кандидат: мелкие детали, антиалиасинг, серифы. Считать надо не «сколько стоит blur», а
«сколько стоит перерастеризовать строку 9.5 rem 54 раза подряд». В Motion есть отдельная
пометка про предупреждение при радиусе > 10 px из-за памяти на мобильных.
**Плюс у нас уже стоит запрет на `backdrop-filter` поверх канваса** (наши грабли на iOS,
`DESIGN-SYSTEM` §6.2). `filter: blur` — не то же самое, но соседняя дверь.
**Вердикт:** только первый блок, ≤ 3 строк, радиус ≤ 5 px, и только за
`gsap.matchMedia('(min-width: 900px)')`. На телефоне — не включать.
**Бесплатная замена, читающаяся похоже:** `scale: 1.035 → 1` + `opacity: 0 → 1`. Даёт то
же «проявление из нерезкости» на composite-only свойствах.

### M7. Пословная подсветка цветом (единственный приём, честно живущий на скрабе)

```js
gsap.fromTo(words, { color: 'var(--muted)' }, {
  color: 'var(--fg)', stagger: 0.06, ease: 'none',
  scrollTrigger: { trigger: el, start: 'top 70%', end: 'top 30%', scrub: 0.4 },
})
```

**Как выглядит.** Текст **всегда виден целиком** приглушённым и «загорается» по мере
прокрутки. Отматывается назад безболезненно — там ничего не пропадает.
**Цена.** `color` — paint-tier (C по классификации Motion): перерисовка на каждый кадр.
Для одного абзаца приемлемо, для одиннадцати блоков — нет.
**Зачем он здесь.** Это доказательство от противного к разделу 3: чистый скраб работает
на тексте **только** тогда, когда текст на всём протяжении читаем. Как только на скрабе
висит появление/исчезновение — читаемость ломается.

## 3. Скраб против триггера

### 3.1. Что даёт чистый `scrub`

`scrub: true` привязывает playhead твина к позиции скроллбара между `start` и `end`.
`scrub: 0.6` добавляет догоняющее сглаживание в 0.6 с. Важно: **`scrub` и `toggleActions`
взаимоисключающи** — при заданном `scrub` `toggleActions` игнорируется.

Плюс ровно один, но он и есть просьба владельца: **связь непосредственная**. Не «камера
поехала, и где-то там текст тоже поехал», а «камера и текст — одна ручка».

### 3.2. Четыре причины, по которым чистый скраб на тексте плох

1. **Отматывается.** Прокрутил на 200 px вверх перечитать — абзац на глазах уползает
   обратно под маску. Это не мелочь: перечитывание на длинной странице — норма, а не
   исключение.
2. **Замирает в середине.** Отпустил колесо на половине окна — строка стоит наполовину
   выехавшей, наполовину срезанной маской. Твин не «идёт медленно», он **стоит**.
3. **Пролетает.** На инерционном флике (trackpad, iOS) 45 % высоты экрана проходят за
   2–3 кадра. Раскладка отыгрывается за 50 мс и её никто не видит.
4. **Требует пина.** Чтобы скраб был читаем, секцию надо пиннить — иначе текст ещё и
   едет по экрану, пока внутри него что-то раскрывается. Пин у нас уже есть на блоках
   1, 2, 5 (`Block hold`), но на 3 и 4 его нет (`hold={false}`), и добавлять его туда
   ради текста — переписывать композицию.

Пункт 2 фатален и не лечится числовым скрабом: сглаживание меняет только скорость
догона, а не то, что playhead равен прогрессу прокрутки.

### 3.3. Храповик — официальный обход реверса

Джек Дойл (автор GSAP) даёт такой рецепт против отматывания:

```js
ScrollTrigger.create({
  trigger: '#hero', start: '-107px', end: '+=120%', pin: true,
  onUpdate: self => {
    if (self.direction === 1 && self.progress > tween.progress()) {
      tween.progress(self.progress)
    }
  },
})
```

Лечит причину 1. Причины 2, 3, 4 остаются.

### 3.4. Рекомендация: храповик на **раскладке**, время — на **строке**

Разделяем две вещи, которые скраб склеивает:

| Что | Чем управляется | Почему так |
|---|---|---|
| **какая строка уже начала ложиться** | прокруткой, монотонно вперёд (храповик) | это и есть «двигается кадр — и строчка стелется» |
| **как строка ложится** | своим временем, 450–900 мс, `e-out` | строка всегда доигрывает до конца и никогда не стоит наполовину |

Что мы получаем по пунктам 3.2:

1. Отматывания нет: уложенная строка помечена и второй раз не трогается.
2. Замирания нет: каждый твин временной, стартовал — доиграл.
3. Пролёта нет: при быстром флике все строки высвобождаются подряд с полом зазора 55 мс —
   получается плотный каскад вместо мгновенного «щелчка».
4. Пин не нужен: мы не требуем, чтобы блок стоял на месте во время раскладки.

И главное — **связь с кадром остаётся прямой и наблюдаемой**: остановил палец на середине
блока → две строки лежат, две ещё нет. Продолжил медленно → они ложатся по одной. Это
буквально то, что просили; при обычном триггере это невозможно в принципе.

## 4. Рекомендуемая реализация

### 4.1. Механика в одном абзаце

Блок «взводится» за экран до выхода: строки прячутся, слои поднимаются. Затем на отрезке
прокрутки длиной `W` (окно раскладки) ScrollTrigger в `onUpdate` считает, сколько строк
**уже должно было стартовать**, и выпускает недостающие. Каждая выпущенная строка играет
свой временной таймлайн M4. Прогресс монотонен по построению (счётчик только растёт).
Если прокрутка встала, а строки остались — через 220 мс выпускаются все оставшиеся.

### 4.2. Регистрация (один раз, `main.tsx`)

```ts
import gsap from 'gsap'
import { useGSAP } from '@gsap/react'
import { ScrollTrigger } from 'gsap/ScrollTrigger'
import { SplitText } from 'gsap/SplitText'
import { CustomEase } from 'gsap/CustomEase'

gsap.registerPlugin(useGSAP, ScrollTrigger, SplitText, CustomEase)

// Токен --e-out = cubic-bezier(0.16, 1, 0.30, 1). CustomEase принимает
// четыре числа как cubic-bezier ровно так же, как CSS (исходник CustomEase.js:156).
// expo.out похож, но это НЕ та же кривая — а у нас в CSS-переходах живёт именно эта.
CustomEase.create('e-out',   '0.16, 1, 0.30, 1')
CustomEase.create('e-inout', '0.65, 0, 0.35, 1')

ScrollTrigger.config({ ignoreMobileResize: true, limitCallbacks: true })

// Пересчёт после раскладки шрифтов — иначе start/end посчитаны по фолбэку.
document.fonts.ready.then(() => ScrollTrigger.refresh())
```

`ignoreMobileResize: true` обязателен: на iOS сворачивание адресной строки меняет высоту
и вызывает `refresh()`, который на середине раскладки сбросит окна. (Сам `autoSplit`
на это не реагирует — он сравнивает только `offsetWidth`, с дебаунсом 200 мс; проверено
по исходнику 3.15.0, строки 185–195.)

### 4.3. CSS, который должен появиться в `index.css`

```css
/* SplitText вешает класс на маску только если он есть у строки: имя строки
   получает суффикс "-mask" (исходник SplitText.js:277). Без linesClass маски
   безымянные и застилизовать их нечем. */
.line,
.line-mask { will-change: auto; }

/* Маска обрезает по padding-box. Наши дисплейные уровни живут на line-height < 1,
   и без запаса маска срезает верхушки букв — см. §1.2. Отрицательный margin
   возвращает раскладку на место. */
.line-mask { padding-block: var(--mask-pad, 0.08em); margin-block: calc(var(--mask-pad, 0.08em) * -1); }
.t-display :is(.line-mask) { --mask-pad: 0.22em; }
.t-h2      :is(.line-mask) { --mask-pad: 0.16em; }

/* Safari < 16 не знает overflow: clip — inline-стиль от GSAP просто отбрасывается,
   и маска перестаёт быть маской (строки видны в скрытом положении). */
@supports not (overflow: clip) {
  .line-mask { overflow: hidden !important; }
}

@media (prefers-reduced-motion: reduce) {
```

### 4.4. Числа

**Скрытое положение строки.** Выводится, не подбирается:

```
yPercent_hidden = 100 × (lineHeight + mask_pad + ink_overshoot) / lineHeight
ink_overshoot   = max(0, (content_area − lineHeight) / 2),   content_area ≈ 1.20 em
```

| Уровень | `line-height` (HE/лат.) | `--mask-pad` | **`yPercent`** |
|---|---|---|---|
| `.t-display` | 0.92 / 0.86 | 0.22 em | **145** |
| `.t-h2` | 1.10 / 1.04 | 0.16 em | **124** |
| `.t-lead` | 1.41 / 1.35 | 0.08 em | **112** |
| `.t-body` | 1.71 / 1.65 | 0.08 em | **110** |
| `.t-caption` | 1.20 | 0.08 em | **112** |

Единое значение 145 для всех тоже работает и почти неотличимо, но на корпусе строка
стартует заметно ниже и первый кадр выглядит пустее. Разница — 5 строк в объекте.

**Окно раскладки** (длина отрезка прокрутки, за который выходят все строки блока):

```
W = vh × (0.45 − 0.22 × v),     v — скорость камеры в этой точке плёнки, 0..1
```

Откуда 0.45: при типичной прокрутке колесом ≈ 900 px/с и четырёх строках зазор между
стартами получается `W / (n·s) = 0.45·800 / (4·900) ≈ 100 мс` — ровно токен из
`DESIGN-SYSTEM` §5.2 для неподвижной камеры. При `v = 1` окно 0.23 vh → зазор ≈ 51 мс,
и это ровно токен для броска. То есть **формула §5.2 не выбрасывается, а
переписывается в пространство прокрутки**: там, где камера летит, окно вдвое короче.

Окно **не** зависит от числа строк — и это намеренно: у длинного абзаца зазор
автоматически сжимается, и низ не заставляет ждать (см. раздел 7).

**Остальное:**

| Параметр | Значение | Почему |
|---|---|---|
| `start` | `top 84%` | строка успевает встать раньше, чем взгляд дойдёт: при 900 px/с точка 84 % доходит до центра за ≈ 300 мс, первая строка к этому моменту отыграла на две трети |
| `end` | `+= W` (функция, `invalidateOnRefresh: true`) | привязка к расстоянию, а не к позиции — иначе `sticky` в `Block` даёт бессмыслицу: элемент прилипает и его экранная позиция перестаёт меняться |
| длительность строки | `900 − v·450` мс | `DESIGN-SYSTEM` §5.2, без изменений; **но берётся в момент выпуска строки** |
| ease | `e-out` | §5.1 |
| пол зазора | **55 мс** | ниже — сливается в один «хлоп»; проверено на 60 fps: 55 мс = 3.3 кадра, порог различения последовательности |
| дожим по простою | **220 мс** тишины | меньше — срабатывает на микропаузах пальца; больше — читатель успевает заметить, что абзац недописан |
| сдвиг (drift) | `0.22 em`, потолок **20 px** | привязан к кеглю: дисплей стелется размашистее корпуса. Потолок — чтобы маска не вышла за поле колонки (`px-6` = 24 px) |
| `skewY` | `clamp(−1,1, v_scroll/2400) × 1.2° × min(1, 480/ширина_строки)` | 1.2° — потолок из §5.3. Множитель по ширине: на строке 700 px наклон 1.2° даёт 15 px вертикального сдвига края — это уже читается как сбой, а не как инерция |
| `transformOrigin` | `left center` / `right center` (RTL) | точка отсчёта у края чтения: голова стоит, хвост догоняет. Это и есть «стелется» |
| прозрачность | только для `display` / `h2`, `0 → 1` за первые 55 % | на крупном кегле край маски слишком жёсткий. Корпусу хватает маски — лишний канал композитинга не нужен |

### 4.5. Референсная реализация

```tsx
import { useRef } from 'react'
import { useGSAP } from '@gsap/react'
import gsap from 'gsap'
import { ScrollTrigger } from 'gsap/ScrollTrigger'
import { SplitText } from 'gsap/SplitText'
import { speedAt, timingFor, windowFor } from '../film/motion'

type Level = 'display' | 'h2' | 'lead' | 'body' | 'caption'

const HIDDEN: Record<Level, number> = {
  display: 145, h2: 124, lead: 112, body: 110, caption: 112,
}
const FADES: Level[] = ['display', 'h2']

const MIN_GAP = 0.055      // с — пол зазора между стартами строк
const IDLE    = 220        // мс тишины прокрутки → дожать оставшиеся строки
const DRIFT   = { em: 0.22, maxPx: 20 }
const SKEW    = { max: 1.2, ref: 2400, width: 480 }

interface Props {
  children: React.ReactNode
  className?: string
  /** локаль: смена пересобирает разбиение и пересчитывает триггеры */
  locale: string
  /** типографический уровень — от него скрытое положение и запас маски */
  level?: Level
  /** положение блока на плёнке 0..1 — из него окно раскладки. Детерминировано,
   *  в отличие от «где пользователь сейчас»: иначе окно менялось бы на каждом refresh */
  film?: number
  /** 'film' — раскладка ведётся прокруткой; 'intro' — блок виден при загрузке,
   *  вести нечем, играем по времени */
  mode?: 'film' | 'intro'
  delay?: number
}

export function Lines({
  children, className = '', locale, level = 'body', film = 0, mode = 'film', delay = 0,
}: Props) {
  const root = useRef<HTMLDivElement>(null)
  /** сколько строк уже уложено — переживает пересборку разбиения */
  const laid = useRef(0)

  useGSAP(
    () => {
      const el = root.current
      if (!el) return

      const mm = gsap.matchMedia()

      mm.add(
        {
          motion: '(prefers-reduced-motion: no-preference)',
          small: '(max-width: 640px)',
        },
        (ctx) => {
          const { motion, small } = ctx.conditions as Record<string, boolean>
          // reduce: не разбиваем вовсе. Текст остаётся текстом — так его видит
          // и поисковик, и скринридер, и DOM не засоряется масками.
          if (!motion) return

          const rtl = getComputedStyle(el).direction === 'rtl'
          const sign = rtl ? 1 : -1
          const origin = rtl ? 'right center' : 'left center'
          const hidden = HIDDEN[level]
          const fades = FADES.includes(level)
          const driftEm = small ? DRIFT.em * 0.6 : DRIFT.em
          const skewMax = small ? SKEW.max * 0.7 : SKEW.max

          const split = SplitText.create(el, {
            type: 'lines',
            mask: 'lines',
            linesClass: 'line',   // ← без этого маски безымянные и не стилизуются
            autoSplit: true,
            onSplit(self) {
              const lines = self.lines as HTMLElement[]
              const masks = self.masks as HTMLElement[]
              let clock = 0      // время последнего выпуска, шкала gsap.ticker

              /** Единственное определение «строка на месте». Им же пользуется страховка. */
              const rest = (i: number) =>
                gsap.set([lines[i], masks[i]], { clearProps: 'transform,opacity,willChange' })

              const hide = (from: number) => {
                gsap.set(lines.slice(from), {
                  yPercent: hidden, ...(fades && { opacity: 0 }), willChange: 'transform',
                })
                gsap.set(masks.slice(from), { willChange: 'transform' })
              }

              /** Уложить строку i. vel — скорость прокрутки, px/с. */
              const lay = (i: number, vel: number, gapMin = MIN_GAP) => {
                // Тайминг берётся ЗДЕСЬ — в момент выпуска строки, а не при разбиении.
                const { duration } = timingFor(speedAt(film))
                const px = parseFloat(getComputedStyle(lines[i]).fontSize) || 16
                const drift = Math.min(DRIFT.maxPx, px * driftEm)
                const w = lines[i].offsetWidth || SKEW.width
                const skew =
                  gsap.utils.clamp(-1, 1, vel / SKEW.ref) *
                  skewMax * Math.min(1, SKEW.width / w) * (rtl ? -1 : 1)

                const wait = Math.max(0, clock + gapMin - gsap.ticker.time)
                clock = gsap.ticker.time + wait

                gsap
                  .timeline({ delay: wait + (i === 0 ? delay : 0), onComplete: () => rest(i) })
                  .fromTo(
                    masks[i],
                    { x: sign * drift, skewY: skew, transformOrigin: origin },
                    { x: 0, skewY: 0, duration, ease: 'e-out' },
                    0,
                  )
                  .fromTo(
                    lines[i],
                    { yPercent: hidden, ...(fades && { opacity: 0 }) },
                    { yPercent: 0, ...(fades && { opacity: 1 }), duration, ease: 'e-out' },
                    0,
                  )
              }

              // ── Пересборка разбиения (шрифт догрузился / изменилась ширина).
              // Что уже лежало — ставим на место мгновенно, без повторной анимации.
              for (let i = 0; i < Math.min(laid.current, lines.length); i++) rest(i)

              if (mode === 'intro') {
                // Блок виден при загрузке — прокруткой вести нечем.
                hide(laid.current)
                document.fonts.ready.then(() => {
                  const { stagger } = timingFor(speedAt(film))
                  for (let i = laid.current; i < lines.length; i++) lay(i, 0, stagger)
                  laid.current = lines.length
                })
                return
              }

              // ── Взвод: за экран до выхода прячем строки и поднимаем слои.
              ScrollTrigger.create({
                trigger: el, start: 'top 100%', once: true,
                onEnter: () => hide(laid.current),
              })

              // ── Раскладка: прогресс прокрутки решает, сколько строк уже стартовало.
              let idleId = 0
              ScrollTrigger.create({
                trigger: el,
                start: 'top 84%',
                end: () => '+=' + window.innerHeight * windowFor(speedAt(film)),
                invalidateOnRefresh: true,
                onUpdate(self) {
                  const want = Math.ceil(self.progress * lines.length)
                  while (laid.current < want) lay(laid.current++, self.getVelocity())

                  // Дожим: прокрутка встала, а строки остались — выпускаем.
                  // Правило §5.4: ни одна анимация не блокирует чтение.
                  window.clearTimeout(idleId)
                  if (laid.current < lines.length) {
                    idleId = window.setTimeout(() => {
                      while (laid.current < lines.length) lay(laid.current++, 0)
                    }, IDLE)
                  }
                },
              })

              return () => window.clearTimeout(idleId)
            },
          })

          return () => split.revert()
        },
      )

      return () => mm.revert()
    },
    // revertOnUpdate обязателен: без него @gsap/react откладывает откат до
    // размонтирования, и каждая смена языка оставляет живой набор триггеров.
    { scope: root, dependencies: [locale, level, film, mode], revertOnUpdate: true },
  )

  return (
    <div ref={root} className={className}>
      {children}
    </div>
  )
}
```

> 🔴 **Поправка 22.08.2026.** В коде выше `onSplit` возвращает функцию уборки — так
> делать нельзя, и в живой реализации этого больше нет. `SplitText` возврат `onSplit`
> использует, только если это анимация (`onSplitResult.totalTime` в исходнике 3.15.0);
> функцию он не вызовет никогда. Значит при каждой пересборке (шрифт догрузился,
> изменилась ширина, сменился язык) поверх нового разбиения оставался живой набор
> ScrollTrigger'ов от старого. Счётчик `laid` у них общий: мёртвый триггер выбирал его
> на оторванных от документа узлах, а живой видел «всё уже уложено» и не трогал ничего.
> Отсюда же предупреждения `GSAP target not found` — `gsap.set` на пустом срезе.
> Триггеры надо держать в списке рядом с разбиением и гасить первым делом в `onSplit`.

## 5. Связка со скоростью камеры (`src/film/motion.ts`)

### 5.1. Правило: одна величина — один канал

Соблазн — подмешать `v` во всё сразу. Тогда при разгоне камеры одновременно укорачивается
длительность, сжимается зазор, растёт сдвиг и растёт наклон — и вместо «текст пошёл
быстрее» получается «текст дёрнулся». Эффект пропадает: когда меняются четыре параметра,
глаз не читает ни одного.

| Канал | Из чего берём | Почему именно так |
|---|---|---|
| **длительность строки** | скорость **камеры** `speedAt(film)` | §5.2, уже посчитано. Единственное изменение — момент вычисления |
| **зазор между строками** | скорость **камеры** — через длину окна `W` | правильный способ «подмешать в stagger»: не задавать зазор числом, а задать отрезок прокрутки. Быстрая камера → короткое окно → строки ложатся чаще, **и при этом зазор всё равно остаётся производной от того, как быстро едет палец** |
| **наклон `skewY`** | скорость **прокрутки** `self.getVelocity()` | 🔴 это другая величина. Скорость камеры — свойство ленты (насколько меняется сцена на единицу прокрутки). Скорость прокрутки — свойство пальца. Инерция наследуется от пальца, темп — от ленты. Смешать их = получить наклон там, где пользователь ничего не делал |
| **направление сдвига** | **направление чтения**, и только | ниже |

### 5.2. Почему направление сдвига нельзя брать из камеры

Камера в `render/scene.py` за ленту меняет направление несколько раз: сближение, налив,
взгляд внутрь. Если подмешать её вектор в сдвиг строки, текст в разных блоках поедет в
разные стороны, а в одном блоке — начнёт менять сторону на ходу. Это читается как сбой
раскладки, а не как хореография, и прямо нарушает §5.4 («ни одна анимация не блокирует
чтение») и §6 (текст поверх кадра и так работает на пределе).

Направление даёт только один источник — направление чтения. От камеры остаётся **знак
наклона** (по направлению прокрутки: вниз — хвост отстаёт вниз, вверх — наоборот), потому
что наклон — это инерция, а не смысл.

### 5.3. Что должно появиться в `motion.ts`

Файл не правлю; вот что в нём нужно (обе функции — чистые, тестируемые):

```ts
/** Окно раскладки блока в долях высоты экрана. Быстрая камера — короткое окно.
 *  0.45 при v=0 даёт зазор ≈100 мс на четырёх строках при типичной прокрутке,
 *  0.23 при v=1 даёт ≈51 мс — те же два числа, что в DESIGN-SYSTEM §5.2,
 *  переписанные из времени в расстояние прокрутки. */
export function windowFor(speed: number): number {
  return 0.45 - Math.min(1, Math.max(0, speed)) * 0.22
}

/** Скорость камеры в фиксированной точке ленты. Нужна вместо useFilmTiming():
 *  окно и длительность должны быть детерминированы положением блока,
 *  а не тем, где пользователь оказался в момент ScrollTrigger.refresh(). */
export { speedAt, timingFor }   // уже есть
```

`useFilmTiming()` в новой схеме **не нужен и должен уйти**: он выводит тайминг из
«где плёнка сейчас», а нам нужно «где на плёнке стоит этот блок». Каждый блок знает свою
долю — она уже расписана в шапке `App.tsx` (0.00–0.20 герой, 0.20–0.44 зерно, …).
Передавать `film={0.10}`, `film={0.32}`, `film={0.59}`, `film={0.82}`, `film={0.95}` —
середины участков.

Побочный выигрыш: `FilmProgress`-контекст перестаёт быть нужен `Lines`, и компонент
становится чистым от React-контекста.

### 5.4. Один цикл кадра, а не два

Сейчас `App.tsx` держит собственный `requestAnimationFrame` на `scroll`, а GSAP крутит
свой тикер. Два независимых цикла на одной прокрутке — это и лишний кадр задержки между
плёнкой и текстом, и прямое нарушение §5.3 («один timeline на страницу»). Прогресс плёнки
должен считаться в `ScrollTrigger.create({ onUpdate })` или в `gsap.ticker.add` — тогда
кадр и строки обновляются в одном такте, и «стелется вслед за кадром» перестаёт быть
метафорой.

## 6. RTL

### 6.1. Что официально сломано, а что нет

Позиция GreenSock (форум, ответ администратора): «SplitText не проектировался под
языки справа налево». Но ломается это **не на всех уровнях разбиения**:

| Разбиение | HE | AR | Вердикт для нас |
|---|---|---|---|
| `lines` | ✅ работает | ✅ работает | **основной режим** |
| `words` | ⚠️ работает на однородном тексте, ломается на смешанном наборе | ⚠️ то же | точечно, с оговорками ниже |
| `chars` | ⚠️ буквы не соединяются, так что визуально уцелеет; но bidi с цифрами и латиницей переставит порядок | ❌ рвёт вязь | **запрещено** |

Почему `lines` безопасны: `SplitText` определяет строки по геометрии bounding-box уже
отрисованного текста — до разбиения bidi-алгоритм отработал, и строка «как её видит
глаз» уже сложилась. Обёртка вокруг готовой строки порядок не меняет.

> 🔴 **Поправка 22.08.2026, по замеру на живом стенде.** «✅ работает» в таблице выше
> неверно: **порядок слов** внутри строки `lines`-разбиение действительно не портит, но
> **сами строки в RTL не находятся вовсе**. Границу строки `SplitText` ставит там, где
> слово «уехало влево» (`SplitText.js` 3.15.0, в `split()`:
> `curBounds.top > lastBounds.top && curBounds.left < lastBounds.left + lastBounds.width - 1`).
> В иврите слово уезжает вправо, второе условие не выполняется ни разу — и весь абзац
> становится одной «строкой». На проде это давало ровно 11 элементов `.line` на 11
> блоков `Lines`, то есть построчного выхода не существовало в принципе, при полностью
> исправной остальной механике. Флага или опции для RTL в 3.15.0 нет — искал по
> исходнику, слов `direction`/`rtl`/`ltr` в файле нет.
>
> **Как лечится (уже в `Lines.tsx`).** Разбиение считается в LTR: на время вызова
> элементу ставится `direction: ltr` и явное выравнивание, после — возвращается как было.
> Набор слов в строке от направления письма не зависит: перенос выбирается по ширинам,
> а порядок слов в потоке один и тот же. Проверено на живом ивритском абзаце — группы
> слов в `rtl` и в `ltr` совпали до символа. Побочное следствие: `autoSplit` приходится
> выключить (свою пересборку он сделал бы уже в `rtl`), а пересборку по шрифтам и по
> ширине вести самим.

Почему `words` рискованны: каждое слово становится отдельным `inline-block`, то есть
отдельным bidi-прогоном. У однородного ивритского текста визуальный порядок
`inline-block`-ов задаётся `direction` контейнера и совпадает с ожидаемым. Как только в
строке появляется число, время или латинское слово (`23:00`, `18 ₪`, `Shachor`),
переупорядочивание внутри строки больше не происходит — и порядок ломается.

### 6.2. Что делает сам SplitText правильно

`_getLineWrapper` (исходник, строка 62) снимает `text-align` с исходного элемента и
ставит его на каждую строку:

```js
textAlign = window.getComputedStyle(element).textAlign || "left";
newLine.style.textAlign = textAlign;
```

То есть выравнивание переживает разбиение. `direction` не копируется, но и не нужен:
строки и маски остаются потомками элемента с `dir`, и наследование работает.

### 6.3. Подводные камни и что с ними делать

1. **Направление определять по элементу, а не по документу.** `document.dir` — не
   источник истины: `.price` в `index.css` уже принудительно `direction: ltr`, и в
   изолированном контексте документ соврёт. Правильно:
   `getComputedStyle(el).direction === 'rtl'`.

2. **`transform-origin` зеркалить.** `left center` в HE — это конец строки; наклон
   пойдёт от хвоста, и «стелется» превратится в «сползает». Нужен `right center`.

3. **Знак наклона зеркалить.** `skewY(+1.2°)` в LTR опускает правый край (хвост).
   В RTL хвост слева, значит знак меняется. Иначе наклон читается наоборот: хвост
   опережает голову.

4. **Сдвиг маски и край экрана.** В HE колонка прижата к правому краю, маска уезжает
   вправо на `drift`. При `drift ≤ 20 px` и поле `px-6` (24 px) она в экран
   помещается. Если поле когда-нибудь уменьшат — потолок надо уменьшить вместе с ним,
   иначе появится горизонтальная прокрутка (`body { overflow-x: hidden }` её проглотит,
   но на iOS это даёт «резиновый» сдвиг всей страницы).

5. **Смешанный набор — изолировать, а не разбивать.** Строкам с ценами, часами и
   латиницей — `unicode-bidi: isolate` (у `.price` уже есть) и `ignore: '.price, .tnum'`
   в конфиге SplitText, если когда-нибудь понадобится `type: 'lines,words'`.

6. **Смена локали `autoSplit` не ловит.** ResizeObserver сравнивает `offsetWidth`
   контейнера — а он при смене HE↔RU не меняется (колонка та же). Меняются длины строк
   и точки переноса. Значит пересборка обязана идти через `dependencies: [locale]` +
   `revertOnUpdate: true`, и после неё — `ScrollTrigger.refresh()`, потому что высота
   блоков поехала.

7. **`t-caption` остаётся латиницей во всех локалях** (`index.css`: «маркировка
   оборудования»). Внутри RTL-контейнера это одна LTR-строка — `lines`-разбиение её не
   трогает, но `transform-origin` для неё логичнее оставить `left center`. Мелочь,
   но заметная: метка `02` стелется в свою сторону.

### 6.4. Как проверять

Тремя языками подряд, на одном и том же блоке, на 360 px и 1440 px:

```
он же на HE — голова строки справа, движение справа налево, наклон хвоста слева
он же на RU — зеркально
он же на EN — как RU
```

Если хоть в одном движение идёт против чтения — знак `sign` или `origin` не зеркалятся.

## 7. Читаемость

### 7.1. Правило и его число

Правило из `DESIGN-SYSTEM` §5.4 (взято у Mat Voyce): **строка обязана встать раньше,
чем до неё дойдёт взгляд.**

Оцифруем. Скорость чтения корпуса — 200–250 слов/мин ≈ 3.5–4 слова/с. Наша строка на
`max-w-[38ch]` — 6–8 слов ≈ 1.8 с на строку. Значит:

- **бюджет на строку**: 1.8 с. Наша длительность 0.45–0.9 с — запас двукратный. ОК.
- **бюджет на весь блок из n строк**: `1.8 × (n − 1)` секунд после старта первой.
  Раскладка обязана уложиться в него. При окне 0.45 vh и прокрутке 900 px/с четыре
  строки укладываются за 400 мс. Запас — 5×.

Опасен не быстрый случай, а **медленный**: пользователь еле ползёт колёсиком. Тогда окно
0.45 vh при 120 px/с растянется на 3 с, и четвёртая строка появится позже, чем читатель
до неё доберётся. Это и закрывает **дожим по простою 220 мс**: как только палец
остановился или почти остановился, оставшиеся строки выпускаются с полом 55 мс.

### 7.2. Как выбирать зазор

Не выбирать. Он производная: `gap = W / (n × v_scroll)`. Задаются только границы:

- **пол 55 мс** — иначе каскад схлопывается в «хлоп»;
- **потолок задаётся не числом, а дожимом** — 220 мс тишины, и остаток укладывается.

Единственное, что стоит проверять руками: чтобы при типичной прокрутке зазор попадал в
80–110 мс. Это и есть токен §5.2 для неподвижной камеры, из него выведено `W = 0.45`.

### 7.3. Блоки из 5+ строк

У нас такие есть: `actTwoText`, `actThreeText`, `spaceText` — на 360 px это 6–9 строк.

1. **Окно не растягивать.** `W` фиксировано → зазор сжимается автоматически: 8 строк в
   том же окне дают ≈ 50 мс вместо 100. Именно то, что нужно: длинный абзац не должен
   заставлять ждать дольше короткого.
2. **С 7 строк — парами.** `want = Math.ceil(progress × ceil(n/2)) × 2` — строки
   выпускаются по две. Восемь строк по одной — это восемь событий, глаз перестаёт их
   считать и видит «мельтешение»; по две — четыре события, ритм сохраняется.
3. **Заголовок и абзац — не одновременно.** Перехлёст из §5.3: абзац стартует на 85 %
   заголовка. В нашей схеме это `delay` на первой строке абзаца ≈ `0.85 × duration`
   заголовка, либо просто разные `start` у двух `Lines` (что сейчас и сделано через
   `delay={0.2}` — сохранить).
4. **Одновременно анимируется не более одного смыслового блока.** Метка + заголовок +
   абзац, стартующие вместе, — это не «стелется», это «страница загрузилась».

## 8. Производительность

Под текстом живёт WebGL-канвас, который скрабит 144 кадра. Это меняет расчёт: свободного
бюджета композитора у нас нет, он весь съеден атласом.

### 8.1. Что анимируем

| Можно | Осторожно | Нельзя |
|---|---|---|
| `transform` (`x`, `yPercent`, `skewY`, `scale`), `opacity` | `clip-path` — точечно, на одиночных строках | `filter: blur` на телефоне; `width/height/top/left`; `color`/`background` покадрово; `text-shadow` |

Это не общая мантра, а следствие §5.4 и наших граблей: `backdrop-filter` уже ломал
композитинг канваса на iOS.

Отдельно: GSAP пишет свойства из main-thread через `rAF`. То есть даже composite-only
свойства у нас **прерываемы** — если main-thread занят декодированием кадра плёнки,
строка дёрнется. Отсюда следующий пункт.

### 8.2. `will-change`: ставить поздно, снимать сразу

Общий совет («держите в CSS») здесь **не подходит**. У нас ~11 инстансов × 3–8 строк ×
2 узла (строка + маска) ≈ **80–150 постоянных слоёв композитора** поверх канваса. На
телефоне это память, которой нет.

Схема:

- **ставим** во «взводе» — за один экран до выхода (`start: 'top 100%'`). Экрана хватает,
  чтобы браузер успел подготовить слой; это не «слишком поздно», о чём предупреждают на
  форуме GSAP;
- **снимаем** в `onComplete` последней строки через `clearProps: 'transform,opacity,willChange'`.

Итог: в любой момент времени слои подняты максимум у двух блоков.

### 8.3. Сколько инстансов и сколько строк

Ограничение не в числе `SplitText`-инстансов (11 — пустяк), а в числе **одновременно
анимируемых элементов**:

| | Десктоп | Телефон |
|---|---|---|
| одновременно едущих строк | ≤ 6 | ≤ 4 |
| одновременно активных блоков | 2 | 1 |

При окне 0.45 vh, длительности 0.9 с и прокрутке 900 px/с четыре строки укладываются за
400 мс, а живут по 900 мс → максимум 4 в воздухе. Влезаем. Если блок длиннее 6 строк,
включается парный режим (7.3) — он же держит и этот потолок.

### 8.4. Мелочи, каждая из которых стоит кадров

- `ScrollTrigger.config({ ignoreMobileResize: true, limitCallbacks: true })`.
- Один цикл кадра (5.4) вместо `rAF` в `App.tsx` + тикера GSAP.
- Триггеры создавать в порядке страницы сверху вниз — так `refresh()` считает быстрее.
- `end` функцией + `invalidateOnRefresh: true`, чтобы окно пересчитывалось от актуальной
  высоты, а не от той, что была при монтировании.
- Не анимировать `.on-scene` `text-shadow` (он статичный — так и оставить).
- **Мерить на реальном телефоне.** В headless — программный растеризатор, цифры врут;
  это уже записано в наши грабли.

### 9.1. Общая сеть вместо таймера в каждом компоненте

Один обработчик на приложение, вместо одиннадцати `setTimeout(2500)`:

```ts
/** Последний рубеж: строка в кадре, спрятана и ничем не анимируется — показать.
 *  Проверяем состояние, а не время: таймер в компоненте срабатывает на норме
 *  (блок в пяти экранах ниже) и не срабатывает на аварии. */
const net = () => {
  document.querySelectorAll<HTMLElement>('.line').forEach((l) => {
    const r = l.getBoundingClientRect()
    const inView = r.top < innerHeight && r.bottom > 0
    const hidden = +gsap.getProperty(l, 'opacity') === 0 || Math.abs(+gsap.getProperty(l, 'yPercent')) > 1
    if (inView && hidden && !gsap.isTweening(l)) gsap.set(l, { clearProps: 'transform,opacity' })
  })
}
addEventListener('load', () => setTimeout(net, 1200))
document.fonts.ready.then(() => { ScrollTrigger.refresh(); setTimeout(net, 400) })
```

Отличия от нынешнего failsafe: проверяется **состояние**, а не время; свойства
сбрасываются через `clearProps`, поэтому сеть не нужно обновлять, когда в анимацию
добавят ещё один канал.

### 9.2. `prefers-reduced-motion`

`DESIGN-SYSTEM` §8 требует одну `gsap.matchMedia()` на страницу, а не `if` в каждом
компоненте. В референсной реализации выше `matchMedia` внутри компонента — это компромисс
ради изоляции; при сборке общего motion-слоя условие переезжает наверх, а `Lines` получает
готовый флаг пропсом. Что важно сохранить в любом случае: **в режиме `reduce` разбиения
не происходит вообще**. Не «разбили и показали», а «не трогали». Разница видна
скринридеру и краулеру.

## 11. Что именно поменять в `src/ui/Lines.tsx`

По пунктам, в порядке от «ломает сейчас» к «улучшает».

1. **`revertOnUpdate: true`** в конфиге `useGSAP`. Без этого каждая смена языка оставляет
   живой набор ScrollTrigger'ов (§1.3). Это баг, а не оптимизация.
2. **Перенести вычисление тайминга из `onSplit` в момент выпуска строки.** Сейчас
   `timing()` вызывается один раз при разбиении, когда `progressRef.current ≈ 0` для всех
   блоков, и вся связка со скоростью камеры не доезжает до экрана (§1.1).
3. **Заменить `useFilmTiming()` на проп `film` + `speedAt(film)`.** Тайминг и окно должны
   зависеть от того, где блок стоит на плёнке, а не от того, где пользователь оказался в
   момент `refresh()` (§5.3). Контекст `FilmProgress` компоненту после этого не нужен.
4. **Добавить `linesClass: 'line'`** в конфиг SplitText. Без него маски безымянные
   (`SplitText` образует имя маски из имени строки) и их нечем стилизовать — а стилизовать
   надо, см. п. 5.
5. **Починить обрезку выносных:** `--mask-pad` + отрицательный `margin-block` на
   `.line-mask` в `index.css`, `yPercent` по таблице 4.4 вместо константы 108. Сейчас
   `שחור` в `.t-display` (`line-height: 0.86`) режется маской постоянно (§1.2).
6. **Убрать `toggleActions: 'play none none reverse'`** вместе со всем твином-на-блок.
   Заменить на два `ScrollTrigger.create`: «взвод» (`top 100%`, `once`) и «раскладка»
   (`top 84%`, `end: '+=' + vh*windowFor(...)`, `invalidateOnRefresh`) с выпуском строк
   в `onUpdate` по счётчику (§4.5).
7. **Добавить горизонтальный сдвиг и `skewY` на маску** с `transform-origin` у края
   чтения (§4.4). Это и есть «стелется»; без него остаётся «выехало».
8. **Зеркалить по `getComputedStyle(el).direction`,** не по `document.dir` (§6.3).
9. **Добавить дожим по простою** — 220 мс тишины прокрутки выпускают остаток (§7.1).
10. **Заменить failsafe:** убрать `setTimeout(2500)` из компонента, вынести общую сеть
    по состоянию на уровень приложения (§9.1). Финальное состояние определить **одной**
    функцией `rest(i)` через `clearProps`, чтобы страховка не знала список свойств.
11. **`will-change` ставить во взводе, снимать в `onComplete`** — не держать в CSS на всех
    строках (§8.2).
12. **Проп `mode: 'film' | 'intro'`.** Первый блок виден при загрузке, вести его
    прокруткой нечем — он играет по времени с зазором `dur/9` (§4.5).
13. **Проп `level`** вместо угадывания: от него скрытое положение и запас маски (4.4).
14. **`prefers-reduced-motion` — через `gsap.matchMedia`,** не через `matchMedia().matches`
    + `return`: сейчас при смене системной настройки на лету ничего не пересобирается.
15. **Опционально, но по делу:** свести `rAF` из `App.tsx` и тикер GSAP в один цикл (§5.4).
    Пока их два, «текст идёт вслед за кадром» верно с точностью до кадра задержки.

Файлы, которых это коснётся, кроме `Lines.tsx`: `src/index.css` (стили маски, `@supports`),
`src/film/motion.ts` (`windowFor`), `src/main.tsx` (`CustomEase`, `ScrollTrigger.config`,
сеть), `src/App.tsx` (пропсы `film` / `level` / `mode` на 11 вызовах).

## 12. Запасные варианты, если рекомендованный не подойдёт

**A. Оставить триггер, добавить только M4.** Минимальное вмешательство: текущая схема
`play none none reverse`, но со сдвигом, наклоном и правильным `transform-origin`. Строки
станут «стелющимися», но связи с движением кадра по-прежнему не будет — просьба
владельца закрыта наполовину. Годится как промежуточный коммит.

**B. Чистый скраб с пином.** `pin: true` на блоке + `scrub: 0.6` + M1. Даёт самую прямую
связь с кадром, но требует пиннить блоки 3 и 4 (сейчас `hold={false}`), то есть
переписывать композицию, и приносит все четыре проблемы из §3.2. Не рекомендуется.

**C. Скраб + храповик Джека на едином таймлайне.** Убирает отматывание, оставляет
замирание в середине. Дешевле в реализации, чем рекомендованный вариант (один твин на
блок вместо цикла), но именно замирание — то, что читатель считывает как «сломалось».

**D. M7 — пословная подсветка на скрабе.** Единственная механика, честно живущая на
скрабе, потому что текст читаем на всём протяжении. Стоит `color`-перерисовки. Уместна
как **разовый приём на одном блоке** — например, на манифесте, — а не как общая схема.
